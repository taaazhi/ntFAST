# Strix против ntFAST — что попробовали и где стена

[Strix](https://github.com/usestrix/strix) — автономный агент для пентеста:
поднимает песочницу, сам исследует цель, ищет уязвимости и пишет отчёт.
Здесь — попытка натравить его на локальный ntFAST через локальную же модель
(Ollama), без облачных ключей и без отправки данных наружу.

Запускать нечем гордиться как «нашли дыру» — важнее то, чему научил сам
прогон. Итог короткий: **на этом железе Strix упирается не в код проекта, а
в размер контекста, и это подтверждает главный инженерный выбор ntFAST.**

## Как запустить

```bash
docker build -t ntfast-strix:local tools/strix
docker run --rm \
  --add-host=host.docker.internal:host-gateway \
  -v //var/run/docker.sock:/var/run/docker.sock \
  -e STRIX_LLM=ollama/qwen2.5:7b-instruct \
  -e LLM_API_BASE=http://host.docker.internal:11434 \
  -e LLM_API_KEY=ollama-local \
  ntfast-strix:local \
  -n -m quick --max-turns 4 \
  -t http://host.docker.internal:8000
```

Бэкенд должен быть поднят на порту 8000 (`curl http://localhost:8000/health`
→ `healthy`). Цель — свой же localhost, на тест которого есть право.

## Стены, по порядку

| Этап | Что было | Итог |
|---|---|---|
| Установка | `pip install strix` ставит **другой** проект — GIS-утилиту стороннего автора | обойдено: нужен `strix-agent` |
| Платформа | `strix-agent` требует Python 3.12+ и собран только под Linux/macOS | обойдено: контейнер `python:3.12` |
| Песочница | внутри контейнера нет CLI `docker`, а Strix запускает песочницу командой `docker` | обойдено: статический бинарник клиента (см. `Dockerfile`) |
| Подключение | песочница поднялась, Ollama ответила | ✅ дошёл до первого вызова модели |
| Вызов модели | контекст Strix не влез в 4 ГБ видеопамяти | ⛔ **стена железа** |

## Где именно встало

Ollama при вызове от Strix упала:

```
llama-server process has terminated: exit status 0xc0000409:
stack-based buffer overrun ... CUDA error: shared object initialization failed
```

Это не конфигурация и не «слабая модель». Та же `qwen2.5:7b-instruct` в тот
же момент отвечала на короткий запрос за секунду. Разница — в **размере
запроса**: системный промпт Strix плюс схемы десятков инструментов дают
десятки килобайт и большое окно контекста. Загрузка такого контекста на
4 ГБ (GTX 1050 Ti) переполнила память и уронила `llama-server`.

## Почему это подтверждает дизайн ntFAST

Одна и та же 7B **пишет заключение по делу за ~20 секунд** и **падает под
Strix**. Модель одна — разное только то, сколько ей дают.

ntFAST кормит модель отобранным минимумом:

- заключение получает выжимку фактов и список разрешённых чисел (~2.5 КБ),
  а не тысячу транзакций;
- агент не читает выписку — он запрашивает данные инструментами, а считает
  система.

Именно поэтому LLM-функции ntFAST работают на скромном железе, а
универсальный агент, сующий в модель всё подряд, — нет. Это не случайность:
маленький, курируемый промпт — сознательный выбор, и Strix показал его цену
наглядно.

## Что нужно, чтобы Strix реально отработал

- **Облачная модель** (Claude / GPT / Gemini) — Strix рассчитан на них, в
  предупреждении сам перечисляет frontier-модели. На них контекст уходит по
  сети и в местную видеопамять не упирается. Ценой ключа и отправки данных
  наружу — для инструмента, работающего с ПД граждан, это отдельное решение.
- **Либо** Ollama в режиме только-CPU (`num_gpu 0`): контекст пойдёт в
  обычную память, краша не будет, но один ход агента растянется, а весь
  прогон — на часы, с низким качеством находок на 7B.

## Вывод

Дальше Strix вести смысла нет. Уязвимости, на которые он нацелен —
аутентификация, ограничение частоты, доступ к чужим объектам, инъекции —
в ntFAST уже закрыты **прицельными тестами**, написанными пониманием кода,
а не переборным сканером на слабой модели:

- инъекция через назначение платежа — `backend/tests/test_schema_and_privacy.py`;
- обход ограничения частоты заголовком — `backend/tests/test_rate_limiter.py`
  и `frontend/e2e/security.spec.ts`;
- доступ к чужому анализу (403) — проверка владельца во всех эндпоинтах
  `analyses.py`.

Strix — сильный инструмент, но его место — CI с облачной моделью на большом
проекте, а не разовый прогон на 4-гигабайтной видеокарте. Файлы (`Dockerfile`,
эта заметка) оставлены, чтобы прогон можно было повторить, когда появится
подходящая модель.
